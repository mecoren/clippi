# 列表渲染性能测试报告（1 万 / 10 万 / 100 万条）

测试对象：`src/ui/clipboard_list.rs` 的 `ClipboardListView`（`gpui_kit::component::v_virtual_list` 虚拟滚动列表）
测试日期：2026-11-22（优化后复测）　构建：`wait` 分支工作区（含 P0/P1 优化，未提交）　基线：`8f2f96d`

> 这是原生 gpui 桌面应用的列表组件，不是 Web 组件，因此没有"浏览器信息"这一项；对应环境为 Windows 桌面 + D3D11 合成器。首轮测试（11-21）发现 10 万/100 万档存在加载硬故障，已修复，本报告是**修复后的正式矩阵**，并保留修复前后对比。

---

## 0. 结论摘要

1. **列表渲染本身与条目数完全解耦**：1 千 / 1 万 / 10 万 / 100 万四档，帧时间全部 5.81–5.88 ms（≈171 FPS，等于 160 Hz 显示器的 vsync 下限），p95 ≤ 8 ms，最大间隔 13–17 ms。虚拟滚动只渲染可见行，这是硬结论。
2. **首次渲染成本基本与条目数无关**：窗口 0.54–0.87 s、列表数据就绪 0.41–0.88 s（≤10 万档），100 万档 1.54–1.61 s；首屏可交互（首批 120 帧统计完成）1.52 s → 3.51 s。100 万档剩余开销来自**全表 COUNT/维护类查询**，不是列表。
3. **内存与条目数解耦**：稳态私有提交 267→271 MB，峰值 467→471 MB，四档几乎持平（优化前随 1.05 KB/条 线性增长、100 万峰值 652 MB）。
4. **真正的新瓶颈在"更新"路径**：复制新内容后"入库"延迟典型 27–256 ms，但当 `max_items` 贴边（本测试的 100 万档）时，每次捕获后的上限裁剪要对全表做 `COUNT`，实测造成一次 **3.5 s 的主线程阻塞**，期间帧率归零。
5. 首轮暴露的两处硬缺陷已修复：`IN (?,…)` 绑定变量超限导致 **32,767 条以上整表加载失败、列表静默变空**；悬停命中 O(滚动深度) 已改前缀和二分。

## 2. 测试方法与指标定义

### 2.1 数据集

SQLite 直写合成剪贴历史（schema 从现有库复制，**内容全部为随机英文词，不含任何真实剪贴板内容**）：70% 单行短文本、20% 多行文本、7% 链接（`meta_type=link`）、3% 带 `rich_data` HTML（触发 `estimate_card_height` 解析分支）；`updated_at` 每条间隔 37 s 递减，写入后 `ANALYZE`。库体积：0.6 / 4.8 / 47.0 / 471.8 MB。

不含图片条目——图片卡片涉及缩略图解码与文件 IO，会把渲染成本与磁盘成本混在一起（见第 7 节偏差说明）。

### 2.2 指标与采集

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 首次渲染 | 窗口出现、`state ready`、`main view ready`、首屏首批帧 | `EnumWindows` 轮询 + 产品自带启动里程碑日志 + `CLIPPI_FRAME_TRACE` |
| 滚动 | 每 120 帧的 `avg/p95/max` 帧间隔 | `src/ui/frame_trace.rs`（采样期主动请求动画帧，空闲也按刷新率出帧） |
| 更新 | 「复制→入库」端到端延迟、期间的帧表现 | `Set-Clipboard` 注入 + 监听库文件（`clippi.db`/`-wal`）mtime 变化 |
| 内存 | 工作集 / 私有提交（稳态与峰值） | 250 ms 采样 `WorkingSet64` / `PrivateMemorySize64` |
| 正确性 | 列表内容、滚动位置 | `PrintWindow(PW_RENDERFULLCONTENT)` 抓应用自身窗口位图核对 |

阶段：启动 → 空闲 8 s → 更新 3 次 → 中速滚动 10 s（25 次/秒）→ 快速滚动 5 s（80 次/秒）→ 静置 4 s。每档 2 轮（1 千条基线 2 轮）。

滚动注入用 `PostMessage(WM_MOUSEWHEEL)`，不抢焦点、不动物理光标；更新阶段先做 STA 探测，剪贴板含图片/文件时整段跳过，纯文本则执行后原样还原。

### 2.3 复现

```powershell
python prepare.py 1000000                                    # 生成隔离目录与数据集
powershell -File run_bench.ps1 -Count 1000000 -Label m1      # 采集
python analyze.py                                            # 汇总
```
脚本在 `%TEMP%\clippi-bench\`（`prepare.py` / `seed_db.py` / `run_bench.ps1` / `analyze.py` / `mem_curve.ps1` / `hover_test.ps1`），不进仓库。

## 3. 各量级结果

### 3.1 首次渲染

| 条目数 | 库大小 | 窗口出现 | state ready | main view ready | 首屏首批帧 |
|---|---|---|---|---|---|
| 1,000 | 0.6 MB | 603 / 654 ms | 408 / 456 ms | 533 / 583 ms | 1,516 / 1,648 ms |
| 10,000 | 4.8 MB | 539 / 556 ms | 415 / 439 ms | 535 / 573 ms | 1,543 / 1,557 ms |
| 100,000 | 47.0 MB | 589 / 657 / 869 ms | 571 / 579 / 882 ms | 741 / 750 / 1,028 ms | 1,784 / 1,815 / 2,373 ms |
| 1,000,000 | 471.8 MB | 543 / 593 / 603 ms | 1,541 / 1,584 / 1,611 ms | 1,984 / 2,039 / 2,055 ms | 3,487 / 3,504 / 3,514 ms |

- **窗口出现与条目数无关**（0.54–0.87 s）：窗口先建，列表数据后到。
- 数据就绪在 10 万以内基本持平（0.41–0.88 s），100 万档 1.54–1.61 s，增量约 1 µs/条——这部分是全表 `COUNT` / 上限裁剪 / 标题栏统计，**不是列表加载**（列表只读首屏 500 行）。
- 「首屏首批帧」比 `main view ready` 多约 1.0–1.5 s，是 120 帧帧统计窗口本身（120 × 5.85 ms ≈ 0.70 s）加首帧前的初始化。

### 3.2 滚动帧率（ms，每 120 帧一组）

| 条目数 | 空闲 avg | 中速滚动 avg | 快速滚动 avg | 静置 avg | p95 上界 | 最大间隔 |
|---|---|---|---|---|---|---|
| 1,000 | 5.84 | 5.81–5.84 | 5.86 | 5.86–5.87 | 8 | 13.9 |
| 10,000 | 5.82–5.86 | 5.84–5.86 | 5.83 | 5.83–5.85 | 8 | 39.2 |
| 100,000 | 5.84–5.85 | 5.83–5.85 | 5.82–5.84 | 5.84–5.88 | 8 | 15.4 |
| 1,000,000 | 5.84–5.88 | 5.85–5.86 | 5.84–5.85 | 5.83–5.87 | 8 | 13.9 |

折算 **170–172 FPS**，四档差异 < 1%，全部等于 vsync 上限（160 Hz → 6.25 ms），说明每帧渲染成本远低于 6 ms。最大间隔 39.2 ms 的那一组出现在 1 万档快速滚动，属外部干扰（同机有视频播放与浏览器），非数据量导致。

深滚动 + 指针悬停（10 万/100 万档，深度约 2,800–4,700 行）：avg 5.88–6.31 ms、p95 ≤ 11 ms、max 23 ms，无可测劣化。滚动跨过已加载页边界时会触发一次增量扩容（`reload: 427 ms items=1000`），扩容瞬间 avg 6.31 ms、max 23 ms，肉眼不可察觉。

### 3.3 更新响应（复制 → 入库）

| 条目数 | 3 次注入的入库延迟 | 备注 |
|---|---|---|
| 1,000 | 311 / 173 / 132 ms；249 / 132 / 133 ms | 轮询间隔主导 |
| 10,000 | 208 / 111 / 105 ms；229 / 132 / 181 ms | 同上 |
| 100,000 | 212 / 67 / 113 ms；201 / 256 / 73 ms | 同上 |
| 1,000,000 | 212 / **3,580** / 27 ms；201 / **3,542** / 116 ms | 尾延迟见下 |

100 万档的 3.5 s 尾延迟有确定原因：每次捕获后 `AppState::handle_*` 调 `db.prune_items_over_limit_preserving(max_items)`，该函数先做一次 `SELECT COUNT(*) FROM clipboard_items WHERE <MAINTENANCE_DELETABLE_PREDICATE>`。本档 `max_items = 1,000,000` 与库内条数贴边，插入后必然 `deletable_count > max_items`，于是每次捕获都在主线程上全表 COUNT 一次（100 万行 ≈ 3.5 s），期间渲染完全停摆——同一轮里滚动阶段**没有任何帧输出**（`scroll: (no batch)`）就是这个阻塞的直接证据。

## 5. 瓶颈定位

### 5.1 【已修复，实测 + 代码确认】条目数 ≥ 32,767 时整表加载失败、列表静默变空

`get_tags_for_items` 把整页 id 拼进一条 `IN (?,?…)`；SQLite `MAX_VARIABLE_NUMBER=32766`（实测 32766 通过、32767 报 `too many SQL variables`）。失败被 `AppState` 的 `unwrap_or_else` 降级为空 `items`，UI 渲染成"暂无条目"，标题栏仍显示真实条数——用户视角是"历史丢了"。触发条件是 `query_limit = max_items × 2 ≥ 32768`，即 `max_items ≥ 16384`。
**已修复**：按 8,000 个 id 分批绑定（`TAG_QUERY_BATCH`）+ `prepare_cached`；标签失败时降级为"不带标签的同一页"而不是丢空；真正的加载失败会在空态显示错误与重试按钮。测试：`tags_for_a_large_page_are_fetched_in_batches`。

### 5.2 【已修复】启动全量预载，成本随历史长度线性

`AppState::new` 一次读 `max_items × 2` 行并对每条解析 `rich_data` 估高，实测 5 µs/条（100 万档 5.4–5.9 s、峰值 652 MB）。
**已修复**：主列表增量分页，首屏 500 行，滚动距页尾不足 3 屏时页宽翻倍（`LIST_PAGE_STEP` / `grow_loaded_page` / `request_next_page_if_near_end`），隐藏窗口时页宽重置。测试：`loaded_page_grows_until_the_result_set_is_exhausted`、`clear_items_resets_the_loaded_page_width`。

### 5.3 【已修复】悬停命中 O(滚动深度)

`pointer_hover_index` 从第 0 行累加高度直到越过视口底边，每次指针事件都要走完滚动深度以上的所有行；`preview_card_bounds`、工具栏定位同形。
**已修复**：新增 `row_offsets` 前缀和缓存（与 `item_sizes` 由 `set_item_sizes` 同步维护），命中改 `partition_point` 二分，O(n) → O(log n)；既有 42 个悬停几何测试经包装函数原样通过。测试：`pointer_hover_skips_rows_above_the_viewport_via_binary_search`、`row_offsets_accumulate_every_height_and_end_with_the_total`。

### 5.4 【未修复，实测】每次捕获的上限裁剪会在主线程做全表 COUNT

`prune_items_over_limit_preserving` 先 `COUNT(*)` 判定是否超限，再决定是否删除。贴边（`max_items ≈ 库内条数`）时每次捕获都付一次全表扫描：100 万行 **3.5 s**，阻塞 UI 与渲染。10 万档同样存在但仅 ~0.3 s 量级，1 万以内 ~30 ms，因此日常配置下不显眼。

### 5.5 【代码级推断，未实测出劣化】刷新时整表重算高度

`resolve_row_heights` 每次刷新遍历全部已加载条目（命中 `height_cache` 的只比较 `updated_at`）。分页后规模是页宽（500 行起），单次刷新毫秒级；增量扩容到数万行时会随页宽线性变慢，与 5.4 叠加时影响可感知。

### 5.6 【观察】vsync 掩盖了渲染成本的分辨率

160 Hz 把可观测帧时间压到 6.25 ms 以下，因此"四档都是 5.85 ms"的正确解读是**渲染成本低于 vsync 预算**，而不是"恰好 5.85 ms"。要测绝对值需临时关闭 vsync 或用 GPU 计时器。

## 6. 优化建议

### P0（已实施）— 让 10 万/100 万能被渲染出来

1. `get_tags_for_items` 分批绑定，解除 32,766 上限。
2. 加载失败不静默：标签失败降级、真失败报错 + 重试。
3. 主列表增量分页，启动成本从 O(历史) 变为 O(页宽)。

### P1（建议）— 把"更新"路径的尾延迟消掉

4. **把上限裁剪移出捕获路径**：捕获后立即 `reload_items` 渲染，裁剪交给后台线程（独立连接）或下一次空闲；或按删除量增量维护可删条数，避免贴边时每次全表 COUNT。这一条能把 100 万档的 3.5 s 冻结降到毫秒级。
5. **按需估算高度**：`resolve_row_heights` 只对"新出现/时间戳变化"的行调用 `estimate_card_height`，其余行用缓存高度直接拼 `sizes`，避免每次刷新遍历整页。
6. **`COUNT` 类指标缓存**：`total_item_count`、可删条数、标题栏统计在 100 万档贡献约 1.2 s 启动时间，可按"写入计数 + 定期校正"换成 O(1)。

### P2（可选）

7. `max_items × 2` 现在只是懒加载的深度上限，不再影响启动；若要进一步降内存，可改成"页数上限"而非"条数倍数"。
8. 卡片高度持久化：分页之后冷启动只解析 500 行，收益已趋近于零，暂不做（避免一次 schema 迁移 + 回写复杂度）。
9. 若将来真要支持"百万级历史随手翻"，把列表数据源换成 keyset 分页（`WHERE (updated_at, id) < (?, ?)`）可让深滚动也不随偏移量退化为 O(offset)。

## 7. 覆盖范围与偏差

- **不是 Web 组件**：无浏览器/JS 堆指标，对应项为 Windows 桌面、D3D11、vsync 160 Hz。
- **100 万档的滚动数据**取自"去掉更新阶段"的独立轮次（`m5`）；含更新阶段的轮次里，3.5 s 的裁剪阻塞把滚动窗口吃掉了（这本身是 5.4 的证据）。
- **合成数据不含图片**：真实"带图历史"的每帧成本会高于 5.85 ms（缩略图解码 + 纹理上传）。
- **更新阶段仅覆盖文本**：剪贴板含图片/文件时整段跳过（避免破坏用户数据），图片捕获链路的延迟未测。
- **共享桌面干扰**：测试期间机器上同时有视频播放与浏览器，偶发 13–39 ms 尖峰；两轮重复趋势一致。
- **vsync 分辨率限制**：见 5.6。
- **未覆盖**：搜索输入（`keyword_scan_limit` 扫描路径）、多选批量操作、同步/中转站视图、快速粘贴窗口在百万级下的表现。
